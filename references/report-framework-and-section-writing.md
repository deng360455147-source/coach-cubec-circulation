# 报告框架确认与分章节写作协议

本协议把报告阶段拆成两个不可越过的模式：先生成可调整的框架，用户明确确认后，再按章节分批撰写。即使用户首轮直接索要完整报告，也必须先完成框架确认；不得在框架尚未确认时输出完整正文。

## 一、模式与状态

| 状态 | 可以做 | 不可以做 | 退出条件 |
|---|---|---|---|
| `FRAMEWORK_DRAFT` | 梳理证据、设计目录、章节任务、论点、图表和缺口 | 写长篇正文、把假设写成结论 | 形成框架版本 |
| `FRAMEWORK_REVIEW` | 根据用户意见调整二三级标题、篇幅和权重 | 改动固定 8 个一级模块、删去五个核心经营维度、偷跑正文或默认用户同意 | 用户明确确认版本 |
| `FRAMEWORK_APPROVED` | 锁定结构、建立一致性台账、安排写作顺序 | 未记录变更就改变主线 | 进入分章节写作 |
| `SECTION_DRAFT` | 每次写一章或一组强相关小节并做批次复核 | 默认一次性写完整报告 | 用户接受该批或提出修改 |
| `REPORT_ASSEMBLED` | 合并、全局校对、评分复核 | 用润色掩盖证据缺口 | 报告门通过 |

“好的”“可以”“按这个写”等只有在上下文明确指向某一框架版本时才算确认。记录：`FRAMEWORK_APPROVED = 版本号 + 日期 + 用户确认语义`。用户随后改变主问题、章节顺序、瓶颈数量或篇幅分配时，升级版本并重新确认受影响部分。

## 二、框架生成输入

开始前读取：

- 已确认企业、地区、题目方向和中心命题；
- 调研计划、证据台账、样本与清洗说明；
- “可写结论/暂不下结论/需补证”清单；
- 2–4 个候选瓶颈、反证与企业现有动作；
- 2026 官方必含模块和五个经营维度；
- 用户希望强调的业态特点、目标篇幅与交付时间。

缺少核心证据时仍可生成框架，但只能把相关内容写成问题、取证任务或 `[待验证假设]`，证据栏写明 P0 缺口；不得用流畅标题把它伪装成已证实事实。只有进入证据台账且能够精确定位到文件/URL和页码、章节、表格、行号或调研记录编号的主张，才可标记 `[已核验:E###]`。只提供证据编号或材料名称、没有提供具体发现、统计结果、原始片段或可读取文件时，视为“证据尚未交付”，相关候选瓶颈仍为 P0。

## 三、框架生成步骤

### 1. 先锁定决策主线

用一句话写清：

> 在【地区/阶段】，企业的【原有优势或机制】与【新变化】发生【错配】，导致【可观察经营后果】；报告将验证【机制】，并为【责任主体】设计【行动组合与验证指标】。

### 2. 锁定 8 个一级模块，再设计二三级目录

分析报告框架确认单的一级目录必须且只能依次为：

1. 目录
2. 概要
3. 引言
4. 案例简介
5. 企业内部及外部分析
6. 发展瓶颈
7. 结论与启示
8. 附录及参考资料

这 8 项不得删除、改名、合并或调序。地区经营专题、商业模式专题、方案、实施、KPI、风险等仍可根据研究问题细化，但只能作为相应一级模块下的二、三级标题：

- 地区与外部环境放入第 5 项；地区变量还应进入战略、运营、竞争、财务和瓶颈的指标或机制。
- 第 5 项必须显式保留“企业战略、商业模式、运营管理、市场竞争、财务状况”五个核心经营维度，不能只在映射表中勾选。
- 五维联动和目标地区经营机制作为第 5 项下的综合分析。
- 症状、根因、方案、实施、KPI、风险和回滚均放入第 6 项的二三级结构，保持“瓶颈—行动—测量”闭环。
- 调研工具、样本、清洗、证据台账、计算过程与补充图表放入第 8 项。

往届国一作品只用于确定二三级章节的功能和论证顺序，不能改变上述固定一级结构，也不能复制其标题创意。

### 3. 给每章写“施工说明”

每章必须填写：

1. 章节任务：只回答一个核心问题；
2. 一句话主张：必须以 `[结构项]`、`[已核验:E###]`、`[待核验]`、`[待调研]`、`[待验证假设]` 或 `[团队判断]` 标记；
3. 子问题/小节：共同完成主张，不重复分框架；
4. 证据 ID、口径、反证和置信度；
5. 方法及其最低数据条件；
6. 预期图表/表格及其要支持的判断；
7. 输出到下一章的逻辑接口；
8. 证据缺口、负责人和截止时间；
9. 建议篇幅比例，而非为了模仿样本页数拉长正文。

### 4. 做六项结构检查

- **固定结构**：一级目录严格且仅为 8 项，所有扩展留在二三级；
- **完整性**：第 5 项的五维经营均有实质落点；
- **互斥性**：同一事实不在 PESTEL、SWOT、五力和画布中重复；
- **因果性**：每章输出进入下章，最终形成问题—机制—行动闭环；
- **地区性**：地区变量进入指标和机制，而非只在背景章出现；
- **可写性**：P0 证据不足的章节不得承载核心结论。

### 5. 只交付框架，等待确认

使用 [report-framework-approval-template.md](../assets/report-framework-approval-template.md) 输出：

- 框架版本与固定 8 项目录；
- 章节论点矩阵；
- 五维与官方要求映射；
- 关键图表和证据缺口；
- 需要用户决定的二三级标题、篇幅和强调项；
- 明确提示：“当前只确认框架，不开始正文。”

首轮标准行为：先说明当前报告阶段门和证据边界，再给中心命题、固定 8 项目录、章节施工表、五维明细、主张—证据登记表、计划图表、证据缺口和建议批次；结尾等待用户调整或确认。不得因用户使用“完整报告”“直接写正文”等措辞跳过此流程。

交付前运行：

```bash
python3 scripts/validate_report_framework.py path/to/report-framework-approval.md
```

只有脚本返回 `PASS` 才能交给用户审阅。脚本确认的是结构、状态和定位字段，不证明证据本身真实；仍须人工打开原文核验。

## 四、框架确认后分章节撰写

### 1. 默认批次

默认每次交付一章，或最多 2–4 个逻辑强相关小节；以用户指定的字数为准。未指定时，优先保证一个可完整审阅的论证单元，不追求一次写长。只有记录 `FRAMEWORK_APPROVED` 后，用户才可调整交付粒度，包括明确要求一次性组装整稿；即使改变粒度，也必须保留章节施工卡、证据复核和跨章一致性检查。

### 2. 每批开写前

先用 [report-section-batch-template.md](../assets/report-section-batch-template.md) 建立批次卡：

- 使用的框架版本与章节编号；
- 本批要证明的主张和对下章的输出；
- 可用证据 ID、口径、反证、待核实项；
- 采用的方法、图表和必要计算；
- 与前文数字、术语、企业动作和瓶颈的依赖关系。

P0 证据缺失时，可写结构、背景或条件性分析；关键句写 `[待团队核实：证据]`，不得填造数字或来源。

### 3. 正文最小论证单元

每个分析小节按以下顺序组织：

```text
结论式标题
  → 证据与口径
  → 时间/地区/竞品/目标对标
  → 机制与替代解释
  → 对瓶颈或行动的含义
  → 反证、边界与待核实项
```

描述性章节也要在段尾说明“这项事实为什么进入后续分析”。方案章节改为：根因—行动—责任—资源—节奏—过程 KPI—结果 KPI—验证—风险—停止/回滚。

### 4. 每批交付后的六项复核

1. **证据反查**：每个数字、事实和引文能回到证据 ID；
2. **口径反查**：地区、期间、单位、样本和业务范围一致；
3. **因果反查**：相关性没有被写成因果，外部条件没有被写成企业根因；
4. **结构反查**：本批完成框架任务，并将明确输出交给下一章；
5. **一致性反查**：术语、瓶颈名、方案名、数字和图表编号与已确认部分一致；
6. **原创反查**：没有复制国一样本或第三方 skill 的表述、数据和图表。

交付末尾列出：本批结论、证据缺口、用户可修改项、对后续章节的影响，并等待用户确认或修改后再继续下一批。

## 五、建议写作顺序

框架按阅读顺序呈现，正文按论证依赖写作：

```text
瓶颈卡与根因链
  → 内部/外部/地区分析
  → 方案与实施测量
  → 案例简介
  → 引言
  → 结论与启示
  → 概要
```

这样能避免先写大量企业背景，最后才发现证据无法支持瓶颈。

## 六、全局一致性台账

从第一批开始持续维护：

- 企业、品牌、子公司、地区和缩写的标准名称；
- 时间范围、样本量、排除规则和数据版本；
- 核心数字主表、公式与单位；
- 研究问题、瓶颈、根因、方案和 KPI 的唯一命名；
- 图表、附录和参考文献编号；
- `[待核实]`、已解决缺口和变更影响。

用户修改已确认章节时，先判断是否影响后续主张、数字、图表、方案或概要，再更新受影响批次；不得只局部润色而留下逻辑冲突。
