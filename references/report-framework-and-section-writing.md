# 报告框架确认与分章节写作协议

本协议把报告阶段拆成两个不可越过的模式：先生成可调整的框架，用户明确确认后，再按章节分批撰写。即使用户首轮直接索要完整报告，也必须先完成框架确认；不得在框架尚未确认时输出完整正文。

## 一、模式与状态

| 状态 | 可以做 | 不可以做 | 退出条件 |
|---|---|---|---|
| `FRAMEWORK_DRAFT` | 梳理证据、设计目录、章节任务、论点、图表和缺口 | 写长篇正文、把假设写成结论 | 形成框架版本 |
| `FRAMEWORK_REVIEW` | 根据用户意见调整二级结果标题、三级概括、篇幅和权重 | 删除固定 11 章、错置五个核心经营维度、偷跑正文或默认用户同意 | 用户明确确认版本 |
| `FRAMEWORK_APPROVED` | 锁定结构、建立一致性台账、安排写作顺序 | 未记录变更就改变主线 | 进入分章节写作 |
| `B01_DRAFT / B01_AWAITING_USER_APPROVAL` | 只写第3章引言与第4章案例简介并复核 | 写第5章以后正文或概要 | 用户明确接受B01版本 |
| `B02_DRAFT / B02_AWAITING_USER_APPROVAL` | 只写第5—7章核心经营分析并复核 | 写瓶颈、方案或结论正文 | 用户明确接受B02版本 |
| `B03_DRAFT / B03_AWAITING_USER_APPROVAL` | 只写第8—11章诊断、行动、结论与复核资料 | 未确认就组装终稿 | 用户明确接受B03版本 |
| `REPORT_ASSEMBLED` | 合并、全局校对、评分复核 | 用润色掩盖证据缺口 | 报告门通过 |

“好的”“可以”“按这个写”等只有在上下文明确指向某一框架版本时才算确认。记录：`FRAMEWORK_APPROVED = 版本号 + 日期 + 用户确认语义`。用户随后改变主问题、章节顺序、瓶颈数量或篇幅分配时，升级版本并重新确认受影响部分。

## 二、框架生成输入

开始前读取：

- 已确认企业、地区、题目方向和中心命题；
- 调研计划、证据台账、样本与清洗说明；
- “可写结论/暂不下结论/需补证”清单；
- 2–4 个候选瓶颈、反证与企业现有动作；
- 2026 官方必含模块和五个经营维度；
- 用户希望强调的业态特点、目标篇幅与交付时间。

缺少核心证据时仍可生成框架，但只能把相关内容写成问题、取证任务或 `[待验证假设]`，证据栏写明 P0 缺口；不得用流畅标题把它伪装成已证实事实。只有进入证据台账且能够精确定位到文件/URL和页码、章节、表格、行号或调研记录编号的主张，才可标记 `[已核验:E###]`。只提供证据编号或材料名称、没有提供具体发现、统计结果、原始片段或可读取文件时，视为“证据尚未交付”，相关候选瓶颈仍为 P0。

## 三、框架生成步骤

### 1. 先锁定决策主线

用一句话写清：

> 在【地区/阶段】，企业的【原有优势或机制】与【新变化】发生【错配】，导致【可观察经营后果】；报告将验证【机制】，并为【责任主体】设计【行动组合与验证指标】。

### 2. 锁定 11 章三级施工框架

分析报告框架确认单的一级目录依次为：

1. 目录
2. 概要
3. 引言
4. 案例简介
5. 企业内部分析
6. 企业外部分析
7. 企业经营模式
8. 发展瓶颈
9. 经营优化方案
10. 结论与启示
11. 附录及参考资料

固定框架把官方“企业内部及外部分析”展开为第 5—7 章，并把国一样本中高频的方案/实施功能独立为第 9 章。五个核心经营维度的主落点固定为：

- `5.1 企业战略`：定位、增长路径、资源组织、地区战略与执行；
- `5.2 运营管理`：产品客户、采购供应、仓配/门店/网点、履约、库存和质量效率；
- `5.3 财务状况`：收入成本、现金周转、效率/单位经济与数据局限；
- `6.3 市场竞争`：同地区同场景对标、企业位置和竞争传导；
- `7.1 商业模式`：顾客价值、渠道关系、收入成本、伙伴与价值获取。

所有固定二三级标题见 [report-framework-approval-template.md](../assets/report-framework-approval-template.md)。概要固定“研究对象与核心问题、主要结论与方案方向”两个二级标题；引言固定“研究背景与选题价值、研究设计与范围”两个正式二级标题，并规划研究框架图；案例简介保持文字精简，但必须有连续年报数字画像和双模型图表。企业内部分析只保留企业战略、运营管理、财务状况三个二级标题；删除6.4和7.4。每个三级标题下必须有2—3行结合项目材料的概括，至少包括“内容概括”和“证据与边界”。

第8章只保留2—4项核心瓶颈，二级标题直接说清“什么问题造成什么后果”；第9章设置同等数量的方案，二级标题直接说清“改善什么结果、采用什么做法”。第8章三级标题统一回答“表现在哪里、为什么出现、带来什么影响”；第9章统一回答“具体怎么做、谁来做/何时做/需要什么、怎么判断有效/何时调整”。

第11章固定六个二级标题：企业重要数据概览、调查问卷、访谈纲要（含知情说明与编码）、参考文献、观察/竞品与现场记录、补充图表与地区对标。六项不得合并、改名或遗漏；具体三级标题见确认单模板。问卷和访谈使用专业母版且与真实执行一致，参考文献按现行GB/T 7714—2025顺序编码制使用期刊式普通段落与悬挂缩进，禁止表格排版。

### 3. 给每章写“施工说明”

每章必须填写：

1. 章节任务：只回答一个核心问题；
2. 一句话主张：必须以 `[结构项]`、`[已核验:E###]`、`[待核验]`、`[待调研]`、`[待验证假设]` 或 `[团队判断]` 标记；
3. 二三级标题：完成固定施工功能；每个三级标题下用 2—3 行说明内容、证据和边界；
4. 证据 ID、口径、反证和置信度；
5. 方法及其最低数据条件；
6. 预期图表/表格及其要支持的判断；
7. 输出到下一章的逻辑接口；
8. 证据缺口、负责人和截止时间；
9. 建议篇幅比例，而非为了模仿样本页数拉长正文。

### 4. 做七项结构检查

- **固定结构**：11 个一级章节及通用二三级施工功能完整；
- **三级概括**：每个三级标题下有 2—3 行内容概括并标明证据状态；
- **完整性**：五个核心经营维度位于固定章节并有实质判断；
- **互斥性**：同一事实不在 PESTEL、SWOT、五力和画布中重复；
- **因果性**：每章输出进入下章，最终形成问题—机制—行动闭环；
- **地区性**：地区变量进入指标和机制，而非只在背景章出现；
- **可写性**：P0 证据不足的章节不得承载核心结论。

### 5. 只交付框架，等待确认

使用 [report-framework-approval-template.md](../assets/report-framework-approval-template.md) 输出：

- 框架版本与固定 11 章三级目录；
- 章节论点矩阵；
- 五维与官方要求映射；
- 关键图表和证据缺口；
- 需要用户决定的2—4项瓶颈与对应方案二级结果标题、篇幅和强调项；
- 明确提示：“当前只确认框架，不开始正文。”

首轮标准行为：先说明当前报告阶段门和证据边界，再给中心命题、精简的固定11章三级框架、每个三级标题下2—3行概括、五维固定落点、2—4项瓶颈及对应方案、主张—证据登记表、缺口和建议批次；结尾等待用户调整或确认。不得因用户使用“完整报告”“直接写正文”等措辞跳过此流程。

交付前运行：

```bash
python3 scripts/validate_report_framework.py path/to/report-framework-approval.md
```

只有脚本返回 `PASS` 才能交给用户审阅。脚本确认的是结构、状态和定位字段，不证明证据本身真实；仍须人工打开原文核验。

## 四、框架确认后分章节撰写

正式写作前读取 [reader-facing-report-style.md](reader-facing-report-style.md)。内部施工卡与读者正文必须分文件维护；内部证据ID、状态、程序路径和复核日志不得进入正文或Word。

B02/B03不得因追求自然语言或图表丰富而改动本确认单的一级、二级或三级标题。正文与视觉的变化只发生在标题下：按 [national-first-b02-b03-writing-visual-patterns.md](national-first-b02-b03-writing-visual-patterns.md) 选择自然段推进、数值表、图形家族、风格模式和页面版式。

### 1. 固定三批

记录 `FRAMEWORK_APPROVED` 后严格按以下顺序交付，不得自行改变粒度或跳过确认：

1. `B01`：第3章引言 + 第4章案例简介；
2. `B02`：第5章企业内部分析 + 第6章企业外部分析 + 第7章企业经营模式；
3. `B03`：第8章发展瓶颈 + 第9章经营优化方案 + 第10章结论与启示 + 第11章附录及参考资料。

每批完成后先导出、渲染和检查对应DOCX，再交用户并停止等待明确确认。只有上一批Word记录为 `ACCEPTED` 才能开始下一批。第2章概要和第1章目录在三批全部接受后根据已证明结论与最终分页生成，不能提前写结论。

### 2. 每批开写前

先读 [section-writing-evidence-protocol.md](section-writing-evidence-protocol.md)，再用 [report-section-batch-template.md](../assets/report-section-batch-template.md) 建立批次卡：

- 使用的框架版本与章节编号；
- 本批要证明的主张和对下章的输出；
- 可用证据 ID、口径、反证、待核实项；
- 采用的方法、图表和必要计算；
- 与前文数字、术语、企业动作和瓶颈的依赖关系。

第4—7章必须先完成专业文献、公开权威机构报告/数据、权威网站、企业官方披露与本项目竞品/消费者/产品/财务分析的适配性检查；第8—10章的差距、根因、方案参数和结论继续回指这些证据或新增的可定位证据。每项来源只服务于其能直接证明的主张；不能为了显示“专业”而机械凑齐来源类别。

B01开写前另读 [annual-report-empirical-methods.md](annual-report-empirical-methods.md)，完成研究框架图、年报数据底稿、四类候选方法审查、恰好两种READY模型的Notebook及图表，并运行双模型计划校验。若少于两种模型通过门槛，将本批状态设为 `MODEL_SELECTION_BLOCKED`，列补数清单后停止；不得把描述性比较包装成市场份额、协同、DID或DEA‑Tobit结果。

P0 证据缺失时，可写结构、背景或条件性分析；关键句写 `[待团队核实：证据]`，不得填造数字或来源。

### 3. 正文最小论证单元

每个分析小节按以下顺序组织：

```text
结论式标题
  → 证据与口径
  → 时间/地区/竞品/目标对标
  → 机制与替代解释
  → 对瓶颈或行动的含义
  → 反证、边界与待核实项
```

描述性章节也要在段尾说明“这项事实为什么进入后续分析”。方案章节改为：根因—行动—责任—资源—节奏—过程 KPI—结果 KPI—验证—风险—停止/回滚。

### 4. 每批交付后的六项复核

1. **证据反查**：每个数字、事实和引文能回到证据 ID；
2. **口径反查**：地区、期间、单位、样本和业务范围一致；
3. **因果反查**：相关性没有被写成因果，外部条件没有被写成企业根因；
4. **结构反查**：本批完成框架任务，并将明确输出交给下一章；
5. **一致性反查**：术语、瓶颈名、方案名、数字和图表编号与已确认部分一致；
6. **原创反查**：没有复制国一样本或第三方 skill 的表述、数据和图表。

内部交付记录列出批次编号/版本、本批结论、证据缺口、用户可修改项和对后续章节的影响；对用户只交付纯读者正文DOCX及简短确认说明。读者Markdown与DOCX必须通过 `validate_reader_facing_report.py`，Word须逐页图文复核并通过清单后，才把状态置为 `B0X_AWAITING_USER_APPROVAL`。收到对该DOCX版本的明确确认后才记录 `B0X_ACCEPTED` 并继续。

## 五、内部准备顺序与对外交付顺序

对外交付严格执行 `B01 Word → 用户确认 → B02 Word → 用户确认 → B03 Word → 用户确认 → 概要/目录/最终Word`。为避免B01写成企业百科，开写前可在内部先核对确认框架中的瓶颈卡、根因链和第5—7章证据任务，但不得把后续章节正文提前交付，也不得把尚未证明的结论写进引言和案例简介。

## 六、全局一致性台账

从第一批开始持续维护：

- 企业、品牌、子公司、地区和缩写的标准名称；
- 时间范围、样本量、排除规则和数据版本；
- 核心数字主表、公式与单位；
- 研究问题、瓶颈、根因、方案和 KPI 的唯一命名；
- 图表、附录和参考文献编号；
- B01/B02/B03 的版本、确认语义、状态和变更影响；
- `[待核实]`、已解决缺口和变更影响。

用户修改已确认章节时，先判断是否影响后续主张、数字、图表、方案或概要，再更新受影响批次；不得只局部润色而留下逻辑冲突。
